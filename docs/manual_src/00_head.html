Orientation

This manual is a reference, not a narrative. You are not expected to read it front to back. Pick a route.

Route A — 30 minutes, "remind me what this does"

Chapter 1 (one page), then the module map table in Chapter 2, then Chapter 11 (focus guide). That is enough to hold the whole system in your head.

Route B — 3 hours, "I want to be able to change things"

1 · The whole thing in one page

Mental model

The question the code answers

Machine-learned interatomic potentials (MLIPs) are fast enough to replace DFT for surface chemistry — if you trust them. This codebase measures where that trust breaks. It runs the same four-stage relaxation chain twice, once with a reference model and once with a candidate model, and records how far apart they drift at every stage.

# the chain — each stage's input is the previous stage's RELAXED output + one fresh change
bulk  ──cut──▶  slab  ──remove an O──▶  vacancy  ──place a fragment──▶  adsorbate
 │               │                       │                              │
 relax          relax                   relax ×N sites                relax ×N sites
                                        keep min-energy               keep min-energy

The two protocols — this is the central idea

The candidate model runs that chain twice, differing only in where each stage's input comes from:

ProtocolEach stage is built from…What the divergence then means
seededthe reference's relaxed previous stage Intrinsic per-stage error. Both models start from identical geometry, so any difference is that one stage's fault.
full_pipelinethe candidate's own relaxed previous stage Accumulated error. Realistic — this is what you'd get using the model for real.

The contrast between the two is the result: seeded says which stage is weak, full-pipeline says whether the weakness compounds.

"Seeded" does not mean what it sounds like It refers to which previous stage's output you inherit — never to starting at the current stage's answer. Starting a stage from the reference's relaxed version of that same stage would be the "flattery trap": the candidate would look great because it started at the finish line. Design doc §3 calls this out explicitly; the code never does it.

Who calls whom

The author's own summary, from oxide_workflow/__init__.py:1, is the best one-paragraph description of the system and worth memorising:

The system in the author's words pipeline.py asks structures.py for a bulk crystal. It sends it to backends.py to be relaxed (which farms it out to worker_relax.py). It hands the relaxed bulk to stages.py to cut a slab, sends that off to be relaxed, hands that to stages.py to make ~6 vacancy structures, relaxes all 6, keeps the best, hands it to stages.py for ~7 adsorbate placements, relaxes all 7. Then it does the same chain with the candidate model, and uses diverge.py to compare the two at every step. checks.py flags anything suspicious, records.py writes it all down, and config.py supplied the numbers throughout.

The one structural trick: subprocess isolation

MACE and FAIRChem live in mutually incompatible conda environments. So the orchestrator never imports a model. Instead backends.relax() writes a POSCAR and a job.json to a temp directory, launches the model env's own Python interpreter on worker_relax.py, and reads the answer back off disk.

# backends.py:107 — the entire abstraction, made physical
proc = subprocess.run([backend.interpreter(), str(WORKER), str(jobfile)], ...)

This is why worker_relax.py imports only ASE and the model package — never pymatgen, never oxide_workflow. The disk is the interface. Keep this in mind: a "backend" is a subprocess recipe, not a Python object with a compute method.
